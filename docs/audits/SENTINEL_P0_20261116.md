## 3. Anomalies démontrées et corrections

### P1-C1 — erreur pendant le refus/annulation IA

SentinelAiApprovalAuthority appelait directement controller.reject lors d'un refus humain,
d'une tentative d'exécution non approuvée et d'une annulation explicite. Une panne de l'horloge
fait volontairement lever une exception au contrôleur ; elle remontait alors au demandeur.
Trois nouveaux cas échouent sur la source transmise avec `Clock unavailable`.
Le helper discard intercepte l'échec et révoque toutes les capacités en cas d'incertitude.
Il ne transforme jamais un refus en succès et préserve l'invalidation permanente de l'horloge.
Après correction : 89 tests IA JVM réussis, dont les 3 nouveaux. Aucun ancien test IA modifié.

### P1-C2 — résurrection d'un état CONNECTED après recul d'horloge

IntegrationRegistry conservait l'observation expirée et recalculait sa fraîcheur uniquement
avec l'heure fournie. Une séquence 1 000 -> 31 001 -> 2 000 ms rendait fraîche une preuve expirée.
Trois des quatre nouveaux tests échouent avant correction. Le registre invalide désormais ses
observations après recul/temps négatif et rejette de nouvelles publications sur cette instance.
Même une baseline optimiste ne devient pas CONNECTED en situation d'horloge invalide.
Récupération : nouvelle instance avec nouvelles observations ; un retour arrière ne restaure
pas les anciennes. L'instance runtime existante est donc indisponible jusqu'à reconstruction
(processus redémarré) si son horloge murale recule : limite volontaire fail-closed.
Après correction : 18 tests d'intégration JVM réussis, dont 4 nouveaux.

### P1-C3 — rejeu de création vocale après fermeture

Une réponse de création conservée dans Redis pouvait être renvoyée après /close ou après
perte de l'index de session : les deux nouveaux cas retournaient 201 au lieu de refuser.
Les deux branches de rejeu vérifient maintenant tombstone, existence et état ouvert de session,
sujet, appareil, identifiant et salle. Fermeture/index absent => 409 ; incohérence => 503 ;
aucun jeton n'est remis dans ces refus. Le fixture de la course d'idempotence modélise désormais
les DEUX index atomiquement écrits par le gagnant ; ses assertions ne sont pas affaiblies.
Sept nouveaux cas couvrent fermeture, index perdu et cinq incohérences de métadonnées.
**Limite : aucun appel de révocation LiveKit n'est implémenté. Un jeton déjà remis reste
potentiellement utilisable jusqu'à son expiration (plafond 120 s) ; corriger le rejeu HTTP
ne vaut pas révocation du média.** Une course commencée avant /close n'est pas annulée à distance.

### P2-C4 — validateur de livraison terminant le processus importeur

check-android-ui-consistency exécutait la vérification du dépôt et process.exit lors de son
import par un test ou outil ; une arborescence absente provoquait aussi une erreur null.includes.
L'export est maintenant importable sans vérification CLI ; le CLI garde ses erreurs et son
code de sortie non nul pour une source manquante. Deux nouveaux tests de subprocess le prouvent.
Les marqueurs InCall obsolètes sont remplacés par les appels begin/complete et les deux kinds
du tracker effectivement utilisé ; le contrôle du dispatcher IO reste obligatoire.

### P2-C5 — contrats/documentation désynchronisés, sans modification téléphonique

- Roadmap publique, protocole et test alignés sur le schéma Phone Core v6 réellement présent.
  Le seuil 14, les flags physiques false et la distinction notification publiée/observée sont
  conservés ; deux assertions supplémentaires empêchent d'en faire une preuve physique.
- Le contrôle de notification accepte le remplacement par une notification d'appel en cours
  seulement après un état Telecom non ringing ; il vérifie aussi les états terminaux et ajoute
  un test d'identité de notification commune. Aucune suppression d'assertion du receiver.
- Le contrôle de nettoyage MMS exige le retour étiqueté Kotlin `return@exclusively Result.retry()`
  et la frontière sérialisée `MmsDownloadRecovery.exclusively`. Le retry reste exigé.
- Un commentaire mentionnant textuellement un nom de credential serveur déclenchait un contrôle
  qui l'interdit dans la source Android. Commentaire reformulé, requêtes réseau inchangées.
- Le test Render vocal exige maintenant /health/ready, comme le Blueprint et le contrôle de
  vérité produit. L'ancien test exigeait /health/live et contredisait l'autre contrôle.
  Un test supplémentaire vérifie disabled => live 200 MAIS ready 503. render.yaml est inchangé.

### P2-C6 — programmes de tests inclus dans l'artefact statique

Le build copiait tout public/, y compris les *.test.js utilisant node:test. Un filtre exclut
uniquement ces programmes, en conservant modules runtime et autres assets. Nouveau test réel
de copie de fichiers/niveaux imbriqués et build final exécutés ; zéro *.test.js dans le dist.
Les tests restent présents dans le dépôt. Aucun site n'a été déployé.
