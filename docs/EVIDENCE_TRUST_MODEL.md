# Evidence / Trust Model

## Purpose

Sentinel must never report a stronger validation state than the evidence actually demonstrates.

## Verification levels

- `UNVERIFIED`: required evidence is missing, malformed, or cannot be attributed.
- `STATIC_VERIFIED`: repository evidence is structurally valid, but execution provenance is not established.
- `CI_VERIFIED`: deterministic checks executed in GitHub Actions and the report commit matches `GITHUB_SHA` for that run.
- `PRODUCTION_VERIFIED`: reserved for independently observed production evidence. CI alone must never emit this state.
- `BLOCKED`: a failed check prevents a positive validation claim.

## Non-equivalence rules

- Code exists != code tested.
- Test exists != test passed.
- Workflow exists != workflow executed.
- Workflow executed != workflow passed.
- Build succeeds != production deployment verified.
- Authorization record is structurally valid != authorization source is authenticated.
- Anti-replay implementation exists != durable anti-replay was exercised against the real store.

## Evidence integrity

Every engineering report receives a SHA-256 evidence hash. The hash is an integrity signal for the report content; it is not a cryptographic claim that the underlying observations are true.

GitHub artifact attestations may later be used for release artifacts to bind provenance to the repository, workflow and commit. Such attestations still do not establish that the software is secure by themselves.

## Production verification

`PRODUCTION_VERIFIED` is deliberately not generated by the current local/CI evaluator. It requires a separate, authenticated deployment observation with explicit environment identity, artifact identity, timestamp, and observable result.
